# Durtles Reborn

Native Android client for WaniKani. Keeps every feature of Smouldering Durtles (Apache 2.0, https://github.com/jerryhcooke/smouldering_durtles, latest 1.2.8 on F-Droid), looks modern, and adds new study tools. "Durtles Reborn" is a working title only: the final name must not contain "WaniKani" and should not be too close to "Durtles".

Source of truth for planning: the "Durtles Reborn � Project Outline" artifact (https://claude.ai/artifact/GhDxwT1LEm42tNFL4UjLEQ), a Claude Docs document. Read it through the Claude Docs connector, not by publishing.

## Current state

Package `com.example.durtlesreborn`, minSdk 24, compile/target SDK 37, AGP 9.5.0 (built-in Kotlin plus the Compose compiler plugin, Kotlin 2.4.21), Gradle 9.x, Java 11 with core library desugaring (`java.time` works on API 24). Not a git repo yet. Versions are in `gradle/libs.versions.toml`.

Stack in use: Compose (BOM 2026.09.00) + Material 3, Room 2.8.5 with KSP 2.3.12, WorkManager, DataStore, OkHttp 5, kotlinx.serialization, coroutines; MockWebServer for tests. Commands: `./gradlew testDebugUnitTest`, `./gradlew assembleDebug`. 227 unit tests pass, including `data/EndToEndTest` (repository -> planner -> quiz -> recorder -> queue -> sync engine -> mock server for a review with a mistake, a lesson, and an offline session; this is the nearest thing to the real write path that does not touch the real account) (DataStore tests use an in-memory store because file-backed DataStore fails to rename files on Windows under JDK 25). The debug APK runs on the `Medium_Phone_API_36.0` emulator with the real token (see "Not done yet" for what has and has not been exercised).

### Behaviour decisions to keep

- Sync order: send the queue first (oldest first), then pull. A 422 on a review drops it (server wins); 5xx, 401, 429 or no network stops the run and keeps the queue. Self-study results are never queued.
- Reviews are posted by subject id; `created_at` is sent only for items older than 5 minutes. Lesson finish = PUT start.
- `allowBackup` is off because the token key cannot be restored on another device.
- Only a lone lower-case `n` becomes ? before a consonant (original quirk kept).
- A wrong answer never shows the reading above the item: the furigana above the character only appears after a correct answer (`ui/AnswerReveal.kt`, tested by `AnswerRevealTest`), so it cannot give the hidden answer away.
- A wrong answer hides the accepted answer (`show_answer_on_wrong`, off by default); the details sheet is one swipe up, or a tap on "Tap to reveal answer", away.
- Quiz feedback sits in a rounded 16 dp box like the item panels: a **green** shade for a correct answer, harmonised with the theme (the green hue leans at most 12� towards the theme's primary, pale on light surfaces and deep on dark ones, `ui/FeedbackColors.kt`), and the theme's **red** `errorContainer`/`onErrorContainer` for a wrong one, with a 1 dp border at 18% of the content colour; the accepted answers and the near-miss/digraph notes live inside the box, and the Next button stays below it.
- `keep_keyboard_open` (on by default) decides what the answer field and the IME do between answers, in reviews and lessons alike: on keeps the field focused and the keyboard up so the next answer needs no tap, off collapses it after each answer and leaves the field to be tapped. Off also means no auto-focus when a question appears, so the Next button is never covered.
- When an answer completes a review item, a toast-like pill appears at the top of the question area, above the characters, with the SRS move — for example "↑ Guru 1 → Guru 2", or the drop for a wrong review — and fades away after two seconds. The move comes from the engine (`SessionEngine.finishedItemStageMove`, `StageMove`), not from the state snapshot, and uses the same rule as the assignment patch. It is drawn by `ui/StageBubble.kt` on the theme's surface with the arrow in `primary` (rise) or `error` (fall); reviews only, never lessons or self-study.
- Back inside a quiz always leaves the session (saving it for Resume), never undoes: undo is deliberate, through the on-screen Undo button or Backspace (the keyboard's delete key) on the shown answer, so a stray back swipe cannot rewind a question.

## Principles

1. Parity first. Nothing the original app does is dropped.
2. Offline first. Every answer is saved on the phone before it is sent. The local DB is the single source of truth; the network only syncs it.
3. Beautiful by default: clear type, smooth motion, light/dark/AMOLED themes, dynamic colour.
4. Respect WaniKani's rules (below).

## Planned stack (confirm in Phase 0)

Kotlin, Jetpack Compose + Material 3, Room, WorkManager, OkHttp with Retrofit or Ktor, DataStore for settings, JUnit + Compose UI tests + MockWebServer. Release on F-Droid and GitHub first, Play Store later.

Architecture layering: screens talk only to use cases; use cases read/write the local DB; the sync engine is the only part that talks to WaniKani.

## WaniKani API and legal rules

- Personal API token only. Never ask for username/password.
- No "WaniKani" in the app name (subtitle with "unofficial" is OK). State near the top of the store description that the app is third-party and unofficial.
- Own visual identity: do not copy WaniKani artwork, mascots or layout. The Crabcroc theme mirrors WaniKani's palette at the user's request; WaniKani's guidelines ask for a distinct identity, so review it before any public release.
- Do not bundle subject content (mnemonics, hints, relationships) and do not use it for profit. Free and open source is the safe model.
- Read `max_level_granted` (3 or 60) from the user endpoint; hide locked levels.
- Base URL `https://api.wanikani.com/v2/`, HTTPS only, `Authorization: Bearer <token>`.
- 60 requests/minute; HTTP 429 over the limit; watch `RateLimit-Remaining`.
- Send `ETag`/`Last-Modified` back as `If-None-Match`/`If-Modified-Since` (304 when unchanged). Use `updated_after` on collections. Cursor paging via `page_after_id`. Cache subjects hard.
- Read SRS stage definitions from the API; never hard-code them.
- Send the API revision header.

## Sync rules

1. First run: page through all subjects and cache them within the rate limit.
2. Later runs: `updated_after` + ETag.
3. Offline answer: save result and new item state locally first, then queue it.
4. Online: send the queue in order, retry with back-off, wait on 429.
5. Review done elsewhere: server wins. Behaviour for a repeated review is unknown, so test it on a spare account.

Answer checking: meaning match with typo tolerance and user synonyms, reading match in kana only, on-device romaji-to-kana converter. Port the original's rules and test cases first.

## Design direction

Calm and fast: big Japanese type (Noto Sans JP / Noto Serif JP), one clear action per screen, spring animations, light haptics, reduce-motion setting, bottom-half primary actions, two-pane tablet/foldable layouts, TalkBack labels, font scaling, contrast checked per theme. Replace the original's blocking toasts with a non-blocking feedback bar.

Screens: Onboarding (token paste, unofficial notice), Home, Review, Answer sheet, Lessons, Item detail, Search, Self-study, Stats, Settings (every original option, grouped and searchable, import/export).

## Release

- `./gradlew assembleRelease bundleRelease` produces a signed APK (`app/build/outputs/apk/release/app-release.apk`, for GitHub and sideloading) and AAB (`app/build/outputs/bundle/release/app-release.aab`, for Play). R8 minify, resource shrinking and `lintVitalRelease` run in the same build.
- Signing material is outside version control: `keystore.properties` (git-ignored) points at `keystore/durtles-reborn-release.p12` (PKCS12, alias `durtlesreborn`, RSA 4096, valid to 2054). Back both up; losing them means no further updates under this identity. Certificate SHA-256 is in `docs/release.md`.
- Bump `versionCode` for every upload. The applicationId is still `com.example.durtlesreborn`, which Play rejects; changing it is a new install identity, so decide before the first public release.
- Without `keystore.properties` the release build is unsigned (F-Droid signs from source). Never publish an unsigned APK as the official one.

## Working conventions

- This directory is not a git repo; do not commit until the user runs `git init` or asks for it.
